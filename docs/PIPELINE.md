# Tagatrend: how it works

Tagatrend measures how Filipino viral terms rise, peak and fade in Google searches, and forecasts where a term goes next. It started as two notebooks on four terms (Sana All, Pabebe Girls, Never Grow Old, Fox Silica). It is now a Python pipeline, a set of GPU forecasters scored on terms they never trained on, and a dashboard with live search.

This page is the high-level design and the model pipeline. It is also served on the website at `/docs`.

## At a glance

```

          │
```

## 1. The data

### What Google Trends returns

Google Trends does not return search counts. Each request returns a 0-100 index relative to the highest point **in that request**, sampled from all searches, with low-volume days reported as 0 for privacy. Three consequences shape everything downstream:

- **Resolution depends on the window.** Up to 269 days returns daily rows, up to about five years weekly rows, anything longer monthly rows. The original notebooks trained on one full-history request per term, so the whole Pabebe Girls spike was a single monthly row.
- **Scales do not carry across requests.** Two requests for the same term are on different scales unless they are aligned.
- **Values are a sample.** The same window pulled on two different days differed by about 6.5 index points on average (section 8 of the notebook). That is the noise floor any forecast is measured against.

### The trend library

Eighteen terms: the four set trends from the notebooks, plus fourteen Filipino viral terms chosen for clear lifecycles across 2010-2025. They are listed in `tagatrend/catalog.py`.

| Group | Terms |
|---|---|
| Set trends | Sana All, Pabebe Girls, Never Grow Old, Fox Silica |
| 2010-2016 | Jejemon, AlDub, Pak Ganern, Charot (the evergreen control) |
| 2017 reversal wave | Lodi, Petmalu, Werpa |
| 2020-2023 | Naol, Budol, Marites, Forda, Dasurv |
| 2025 | What Haffen Vella, Trentahin |

Each term is searched as typed, in the Philippines (`geo=PH`). Like the notebooks, these are search terms, not confirmed origins of a trend.

### Building a term (`tagatrend/series.py`)

For every term, `build_term` makes four things:

1. **Monthly backbone.** One request from 2004 to the end date. It finds the peak month and covers the full history.
2. **Weekly series.** Overlapping four-year windows (one-year overlap) from two years before the peak month to four years after it.
3. **Daily series.** One 260-day window starting 75 days before the peak month, so the rise, the peak and the decay are all daily. The set trends keep the notebook's hand-picked windows (Sana All daily covers 2019-2021).
4. **Regions.** Interest by region in the peak week and in the last 30 days.

**Stitching** (unchanged from the notebook). Each new window is multiplied by `sum(previous overlap) / sum(new overlap)` over dates where both are positive. Overlapping values are averaged, and the result is rescaled so its maximum is 100. When the tail windows are all zeros and cannot be aligned, they are dropped rather than forced.

**Pull archive.** Every response is cached in `data/raw/` with a metadata sidecar and archived by pull date in `data/raw/pulls/`. Pulls of the same window from different days are averaged, so rerunning the build on another day reduces sampling noise.

**Dropouts.** A 0 right after a busy week (trailing 7-row median of at least 10) is a low-volume dropout, not zero interest. It becomes missing. The rule reads only past values.

**Rate limits.** Requests are spaced at least 12 seconds apart through one reused session. On HTTP 429 the fetcher backs off for 1, 2, 4, 8 and then 15 minutes. A failed window is skipped, and the next build picks it up from the cache.

## 2. Descriptive analysis (`tagatrend/analysis.py`)

These are computed on the daily series when it exists (else weekly), with a centred 7-day mean to smooth weekday noise.

| Measure | Definition |
|---|---|
| Peak day | The highest raw day near the smoothed peak |
| Before / peak / after weeks | The Monday-Sunday weeks around the peak day; a mean is shown only when all 7 days exist (notebook section 5) |
| Onset | The last day before the peak that the smoothed level was under 10% of the peak |
| Rise | Days from onset to peak |
| Half-life | Days from the peak until the smoothed level first falls under 50% |
| Fade | Days from the peak until it first falls under 10% |
| Left after 4 weeks | The smoothed level 28-34 days after the peak, as a percentage of the peak |
| Shape | Flash (half-life of 7 days or less), Wave (45 days or less), Slow burn |
| Resurgences | Secondary monthly peaks with a prominence of at least 15 points |

**Phase now.** The phase uses the finest series that reaches the end of the data (daily, then weekly, then monthly). That way a spike that peaked and died inside one month is not read from a monthly row that still contains the peak. With *recent* as the last 28 days, 4 weeks or 3 months against the all-time (smoothed) peak:

- **Peaking**: within 21 days of the peak and still at 40% or more.
- **Rising**: at least 15%, and up 30% on the previous window.
- **Evergreen**: the monthly median over two years is at least 25% of the peak.
- **Dormant**: under 8%.
- **Fading**: anything else past its peak.

## 3. Forecasting

### The task

From a forecast date (the *origin*), predict the next **28 days** (daily models) or **12 weeks** (weekly models), as a median and an 80% band (10th to 90th percentile).

### Leakage-free scaling (`tagatrend/features.py`)

A stitched series is scaled so its eventual maximum is 100, so the raw level leaks the future: a value of 100 means the peak has already happened. Every window is therefore divided by **the highest value seen up to the origin** (the peak so far). Forecasts are multiplied back afterwards. Models learn the shape of a lifecycle relative to what was knowable at the time.

The inputs for each origin are:

- the last 42 days (or 26 weeks), divided by the peak so far;
- the window's maximum, the means of the last and previous 7 periods, and growth between them;
- the log-slope of the last 14 periods;
- the time since the peak so far, the time since the window's maximum, and the term's age;
- the day of the week (daily only).

Zeros right after steady nonzero days (28-day rule, floor 5 points) are masked as censored, as in `google_trends_ml.ipynb`. Masked inputs are filled forward from the past, and missing targets are never trained on or scored. An origin is used only once the term has reached 3 points.

### The models

| Model | What it is | Where it runs |
|---|---|---|
| Naive | Repeat the last observed value (the notebooks' baseline) | CPU |
| Mean of last 7 | Repeat the mean of the last 7 periods | CPU |
| Drift | Extend the last two weeks' log-slope, capped | CPU |
| XGBoost | One gradient-boosted model for every horizon (the horizon is a feature), trained with quantile loss at 0.1, 0.5 and 0.9 on all terms pooled | GPU (`device="cuda"`, verified after training) |
| MLP | Two hidden layers of 64, GELU, dropout and input noise, one pinball-loss output per horizon and quantile; the median of 5 seeds | GPU (PyTorch, CUDA 13) |
| TimesFM 2.5 | Google's 200M-parameter pretrained forecaster (Apache-2.0 weights), zero-shot: it never trains on these terms | GPU |
| Ensemble | XGBoost, MLP and TimesFM quantiles, weighted by 1 / MAE² on the training terms' validation rows | |

Both learned models train **in log space** (`log1p(100 * x)`). Spikes are multiplicative, and a quantile survives any monotone transform, so the back-transformed median is still the median. Quantiles are sorted so they never cross.

**Anchored on persistence.** The learned models predict the log-change from the last observed value, not the level. "No change" is then exactly the naive forecast, and a model only has to learn when and how far a term departs from it. On the provisional backtest this moved the weekly MLP from −32% to +10% skill and the weekly XGBoost from −9% to +2%.

**Weighted ensemble.** Inside each fold, every learned model forecasts the training terms' validation rows (the last 20% of each term's origins). The ensemble weights are 1 / MAE² on those rows, normalised. The held-out term is never used to choose them. The production weights come from the final all-terms split and are stored in `data/models/<freq>/meta.json`.

**Why global models.** One term has a few hundred daily rows, and most of them are a dead tail. A single model trained on every term's lifecycle at once learns what a rise, a peak and a decay usually look like, and a new term borrows that from the start. The notebooks' per-term MLP lost to the last-value baseline by 500% on Never Grow Old for exactly this reason: its decay fell into validation and it never saw one.

### How the models are scored (`tagatrend/evaluate.py`)

**Grouped leave-one-term-out.** For each held-out term, XGBoost and the MLP are trained on every other term, then forecast every origin of the held-out term. This is the real use case: a new term appears, and only other terms' histories exist. Terms from the same wave are held out together (Lodi, Petmalu and Werpa; Sana All and Naol), so a sibling cannot leak the answer. Early stopping uses the last 20% of each training term's origins. TimesFM needs no folds, because it never trains on these terms.

**What is scored.** Every origin where the window or the future reaches 10% of the peak so far. That excludes the long dead tails where repeating zero looks perfect; the notebooks' 0.000 Pabebe baseline came from exactly such a tail.

**Metrics.**

- **MAE in index points**, on the term's own 0-100 scale, which is the unit the notebooks report. Errors are also kept in points of the peak so far, but that unit over-weights early origins where the scale is still tiny, so it is not used for skill.
- **Skill**: `1 - MAE(model) / MAE(Naive)`. Positive means the model beat repeating the last value.
- **80% coverage**: the share of outcomes inside the q10-q90 band (nominal 80%).
- **Breakdowns** by horizon, by term, and by lifecycle phase: *Rise* (before the eventual peak), *Peak* (0-14 days after it) and *Decay* (later). The phase labels use the future and exist for scoring only.

### What the results mean

- **Nobody forecasts the explosion.** In the rise phase, before a term peaks, every model is close to or worse than repeating the last value. Search data alone cannot see a spike coming; that is the gap the next phase targets (section 6).
- **Once a term has peaked, its decay is predictable.** Peak and decay are where the global models and TimesFM earn their skill. That is the lifecycle knowledge pooled across terms.
- **Weekly beats daily.** Daily values carry Google's sampling noise of about 6 points; weekly rows average it out.
- **Differences under about 6 points are within Google's own noise** between pull days. Averaging more pulls per window (rerun the build on different days) lowers it.

## 4. The website

**Flask API (`server/app.py`).**

| Endpoint | Returns |
|---|---|
| `GET /api/trends` | The library: every term's phase, lifecycle, shape and yearly strip, plus recent searches |
| `GET /api/trends/<slug>` | One term: all series, the analysis summary, regions and provenance |
| `GET /api/trends/<slug>/replay/<freq>` | Out-of-fold forecasts every 7 days (or 2 weeks), for the replay slider |
| `GET /api/trends/<slug>/forecast/<freq>?origin=` | A live forecast from the production models plus TimesFM, from any date |
| `POST /api/search` | Starts a live pull of a new term; poll `GET /api/search/<id>` |
| `GET /api/models` | Backtest metrics for the Models page |
| `GET /api/docs` | This document |

**Live search.** Typing a term that is not in the library runs the same `build_term` pipeline in a background thread: monthly, weekly, daily, regions. The page polls for progress, then opens the term. Searched terms are stored in `data/search/` and are never trained on, so their forecasts are out-of-sample by construction.

**Screens.** Overview (the four set trends, the library, and every term's lifecycle on one axis), Library, a page per term (search interest, the weeks around the peak, forecast replay, regions, provenance), Models and Docs. The design follows the framed-sheet app style, with colour only on data: observed interest in the Philippine flag's blue, forecasts in the sun's amber, peaks in the flag's red.

## 5. Running it

```bash
# Python 3.12 environment with CUDA PyTorch (RTX 50-series needs CUDA 12.8+ wheels)
uv venv --python 3.12 .venv
uv pip install --python .venv torch --index-url https://download.pytorch.org/whl/cu130
uv pip install --python .venv -r requirements.txt

.venv/Scripts/python scripts/build_dataset.py     # pull + stitch (reuses cached pulls)
.venv/Scripts/python scripts/train_models.py      # backtest + train on the GPU

cd web && npm install && npm run build && cd ..
.venv/Scripts/python server/app.py                # http://127.0.0.1:5000
```

For frontend work, run `npm run dev` in `web/` (Vite on port 5173, proxying `/api` to Flask).

## 6. Next: Reddit and NLP

The current models recognise patterns in the search curve itself. They are good once a term is moving and blind before it moves. The next phase adds a signal that comes **before** the search spike: people asking what a term means.

- **Collection.** Reuse uyam's Shreddit collector: headful Chrome with Patchright, a proxy pool, and the same `SubmissionRecord` and `CommentRecord` schema stored as JSONL with SQLite dedup. Collect from Filipino subreddits (r/Philippines, r/phinvest, r/CasualPH and others) by calendar walks of `/new`.
- **Signals.** Mentions of each term per day; "meaning" questions ("pabebe girls meaning", "what is pabebe", "ano ang ...") in posts and comments; the spread across subreddits; and code-switched usage measured with uyam's language ID.
- **NLP.** Term discovery (new n-grams whose frequency jumps against a baseline), classification of definition-seeking questions, and Taglish-aware embeddings to group spelling variants (Naol, Na all, Sana all).
- **Modelling.** Feed lagged Reddit features into the global forecasters as covariates (TimesFM supports covariates through XReg). Then test whether they move skill in the rise phase, which is where pattern recognition fails today.
- **Validation.** The same grouped leave-one-term-out backtest, comparing skill in the rise phase with and without the Reddit features.
